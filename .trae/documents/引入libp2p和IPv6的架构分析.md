# 架构分析：引入 libp2p（NAT打洞）和 IPv6 作为隧道组成部分

## 当前架构概览

MC Link 的隧道系统架构如下：

```
客户端A(NAT) → TCP → 中继1(Public) ←→ 中继2(Public) ←→ 中继3(Public) ← TCP → 客户端B(NAT)
```

* **中继服务器**：有公网 IP，彼此通过 TCP 连接，使用自定义隧道帧协议（TunnelFrameHeader）多跳转发

* **客户端**：Tauri 桌面应用，总是通过出站 TCP 连接到中继服务器（因此 NAT 类型不影响连接能力）

* **中央服务器**：管理拓扑图、Dijkstra 路径计算、房间管理

* **隧道协议**：自定义二进制帧（30字节头 + 负载），通过 `hop_index` 确定当前节点位置，逐跳转发

* **NAT 穿越**：**不存在** —— 当前架构完全不依赖 P2P 直连

***

## 1. 引入 libp2p 实现 NAT2/NAT3 打洞分析

### libp2p 能做什么

libp2p 提供了完整的 NAT 穿越栈：

* **AutoNAT**：自动检测节点是否在 NAT 后

* **DCUtR (Direct Connection Upgrade through Relay)**：通过中继节点协调打洞，适合 NAT2（受限锥形）和 NAT3（端口限制锥形/对称型）

* **Circuit Relay**：当打洞失败时，通过中继回退转发

* **Identify Protocol**：自动发现节点地址（IPv4/IPv6/多地址）

### 在当前架构中的定位

当前所有流量都通过中继服务器转发。引入 libp2p 后，可能的形式：

#### 方案A：libp2p 作为客户端 ↔ 中继的连接层替换

```
客户端A → [libp2p连接] → 中继1 ←→ 中继2 → [libp2p连接] → 客户端B
```

* 用 libp2p 的加密/多路复用流取代原始 TCP

* 利用 Circuit Relay / DCUtR 让客户端以最小配置连接到中继

* **问题**：当前客户端已经能通过出站 TCP 正常连接中继，NAT 不是障碍。引入 libp2p 增加复杂度但无实质收益

#### 方案B：libp2p 实现 P2P 旁路直连（推荐）

```
客户端A(NAT2) ←→ [libp2p P2P打洞] → 客户端B(NAT3)
                    ↕ (fallback)
       中继1 ← TCP → 中继2 (回退到现有隧道)
```

* 隧道路径计算时，若两端在同一中继上，尝试 libp2p P2P 直连

* 打洞成功后，流量绕过中继服务器直达对方

* 打洞失败时，回退到现有中继隧道

* **收益**：减少中继带宽消耗（尤其对已登录用户8Mbps限速），降低延迟

* **挑战**：需要修改隧道帧协议支持 `P2P` 段；libp2p 与现有加密协议（GCM + 自定义）不兼容；对称 NAT 打洞成功率低

#### 方案C：仅用于中继间的控制面通信

* 中继之间的心跳、拓扑探测改用 libp2p

* 数据面仍保持现有 TCP 隧道

* **收益有限**：中继间 TCP 已正常工作，增加 libp2p 只是替换传输层

### 引入 libp2p 的技术成本

| 维度      | 评估                                                   |
| ------- | ---------------------------------------------------- |
| 编译时间    | 依赖链长（protobuf, multihash, noise, yamux 等），LLVM 链接时间长 |
| 二进制体积   | libp2p 约增加 5-15MB                                    |
| 学习曲线    | 概念多（PeerId, Multiaddr, Stream, Protocol, Swarm）      |
| 维护复杂度   | 版本升级频繁，API 不稳定                                       |
| 与现有协议兼容 | 完全重写隧道帧 vs 并行运行两套协议                                  |

### 对 NAT2/NAT3 的具体效果

* **NAT2 (Full Cone / Restricted Cone)**：打洞成功率高（>90%），libp2p DCUtR 成熟

* **NAT3 (Port Restricted Cone / Symmetric)**：

  * 端口限制锥形：成功率中等（\~60-70%），需要精准的端口预测

  * 对称型：打洞成功率低（<30%），需要第三方辅助（如同时发起到多个端口的猜测包）

* **结论**：无法保证 100% 打洞成功，必须保留中继 fallback

## 2. IPv6 作为隧道组成部分分析

### 当前 IPv6 状态

* `RelayNode.address` 存储为 `String`，解析为 `SocketAddr`（原生支持 IPv6）

* `mc-link-common` 的 Proxy Protocol V2 解析支持 IPv6（第62-74行）

* 但**没有** IPv6 特定的路径优化、双栈选择或地址偏好逻辑

### IPv6 的优势

* **消除 NAT**：拥有公网 IPv6 的客户端无需 NAT 穿越，可直接 P2P 连接

* **降低延迟**：IPv6 通常路由更优（无 NAT 转换延迟）

* **国内 IPv6 普及**：2026年国内 IPv6 活跃用户 > 7亿，家庭宽带覆盖率 > 70%

### 集成方式

#### 在隧道中引入 IPv6 的层次

1. **中继注册与路径表**（低难度）：

   * 中继注册时同时上报 IPv4 和 IPv6 地址

   * 路径表中的 `address` 字段扩展为 `addresses: Vec<String>`

   * 中央服务器根据两端能力选择最优地址族

2. **客户端地址选择**（中难度）：

   * 客户端获取中继列表后，优先选择 IPv6 连接（如果本地有公网 IPv6）

   * 在 FlashConnect/GaojiConnect 中展示 IPv6 连接状态

3. **P2P 直连路径**（高难度，与 libp2p 或独立实现结合）：

   * 当两客户端都有公网 IPv6 时，完全绕过中继

   * 隧道路径变为 `[P2P]`，无需中间跳

4. **路径计算加权**（低难度）：

   * IPv6 链路在 Dijkstra 中赋予较低权值（因为通常延迟更低）

   * 支持双栈中继在两个地址族上的不同延迟上报

## 3. 综合建议

### 推荐策略：IPv6 优先，libp2p 暂缓

**理由：**

1. **当前架构的 NAT 问题已被解决**：客户端通过出站 TCP 连接中继，不存在 NAT 连接障碍。引入 libp2p 解决的是 "客户端之间直连" 问题，而非 "客户端无法连接" 问题

2. **libp2p 成本高、收益不确定**：

   * 需要同时维护两套协议栈

   * 打洞成功率的不可靠性要求保留完整的中继 fallback

   * 对于联机场景（MC Link 为多人游戏），多了一条中继跳的延迟增加通常 <50ms，P2P 直连的收益很小

3. **IPv6 的收益确定且实现成本低**：

   * 不需要额外的库依赖

   * 完全在现有 SocketAddr 框架内

   * 随着 IPv6 普及率提升，越来越多的客户端可直接通过 IPv6 地址互相连接

### 实施路线图

#### 第一阶段：IPv6 基础支持（推荐立即实施）

1. **中继注册扩展**：

   * \[central-server/src/relay.rs] 中继注册指令 (0x10) 扩展 payload，支持 IPv4/IPv6 双地址上报

   * \[mc-link-relay/src/main.rs] 中继启动时自动检测 IPv6 地址，上报给中央服务器

   * \[central-server/src/types.rs] `RelayNode` 添加 `address_v6: Option<String>` 字段

2. **路径表扩展**：

   * \[central-server/src/path.rs] `PathHop` 添加 `address_v6: Option<String>`

   * Dijkstra 路径计算中，若两端节点都有 IPv6，优先使用 IPv6 连接

   * \[mc-link-relay/src/relay.rs] `handle_tunnel_frame` 转发时优先选择 IPv6 地址

3. **客户端 IPv6 偏好**：

   * \[src-tauri/src/central.rs] 获取中继列表后，若本地有公网 IPv6，优先连接中继的 IPv6 地址

   * \[src-tauri/src/host.rs] 连接中继时尝试 IPv6 优先

#### 第二阶段：IPv6 P2P 直连（可选）

1. **客户端之间 IPv6 P2P**：

   * 当房主和成员在同一中继上，且都有公网 IPv6 时，绕过中继直接建立 TCP 连接

   * 中央服务器在 `assign_room_path` 时识别此场景，推送 `P2P` 类型路径

   * 客户端新增 `p2p_listener` 和 `p2p_connector` 模块

#### 第三阶段：libp2p 评估门槛（暂不实施，记录为未来可能性）

当满足以下 **任意一项** 条件时重新考虑 libp2p：

* 用户规模达到 10 万 DAU，中继带宽成本成为主要支出

* 出现需要穿越对称 NAT 的明确用户需求，且 IPv6 无法解决

* 需要支持移动端（手机 NAT 更严格），且现有 TCP 出站方案不够

**替代方案**：在需要 P2P 时，可以使用更轻量的方案：

* 独立 STUN/TURN 库（如 `stunclient` crate，仅 \~200KB）

* 轻量 ICE 实现（如 `webrtc` crate 的 ice 子模块，比全量 libp2p 轻 10x）

* 自行实现 UDP 打洞（约 500 行代码，参考 pwnat 原理）

## 4. 架构影响总结

| 特性       | 当前状态     | 引入IPv6     | 引入libp2p      |
| -------- | -------- | ---------- | ------------- |
| NAT2 连接  | 通过中继正常工作 | 不变         | 可P2P绕过中继      |
| NAT3 连接  | 通过中继正常工作 | 不变         | 部分可P2P(\~60%) |
| 公网IPv6用户 | 通过中继（浪费） | 可直接连接中继    | 可直接连接         |
| 延迟       | 中继转发     | IPv6可能更优   | P2P最优         |
| 中继带宽消耗   | 全量       | 降低（IPv6直连） | 降低（P2P）       |
| 实现复杂度    | -        | 低（\~3文件修改） | 高（大量依赖）       |
| 二进制体积影响  | -        | 无          | +5-15MB       |
| 长期维护成本   | -        | 低          | 高             |

## 5. 结论

* **IPv6 支持**：推荐实施。成本低、收益确定、与现有架构兼容。建议从阶段一（双栈地址 + 路径偏好）开始

* **libp2p 引入**：**不推荐在当前阶段实施**。当前架构已解决 NAT 连接问题，libp2p 的 P2P 打洞收益对游戏联机场景有限，但引入的成本和维护负担很高
