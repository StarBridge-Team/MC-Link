## MC Link 前端架构优化建议

> 基于对现有代码库的阅读和分析，整理以下可供参考的优化方向。
> 不作为硬性需求，仅提供一些思路供后续迭代时参考。

---

### 一、组件与逻辑拆分

#### 现状

- `GaojiConnect.vue`（约 800 行）承载了三种联机协议（MC Link / Revamp / Terracotta）的启动逻辑、UI 渲染、日志管理等多重职责
- `FlashConnect.vue`（约 580 行）的 `hostAll()` 串行依次启动多个服务，任一失败不影响后续但仍缺乏容错
- 核心联机逻辑散落在组件内部，与 UI 耦合较深

#### 建议方向

**1.1 将联机逻辑从组件中抽离为 composable**

参考结构：

```
composables/
  useOnline.ts         # 联机核心逻辑（start/stop/状态管理）
  useOnlineLog.ts      # 日志管理与事件监听
  useOnlineLatency.ts  # 延迟检测与更新
```

- `useOnline` 封装所有联机协议的启动/停止逻辑，返回状态和方法
- 组件只负责 UI 渲染和事件绑定，不再直接调用 API
- 这样 `GaojiConnect` 和 `FlashConnect` 可以复用同一套逻辑

**1.2 FlashConnect 的串行启动改为并行或容错模式**

- `hostAll()` 中 MC Link / 陶瓦联机 / Revamp 三者独立可并行发起
- 任一失败不应阻塞其余服务

### 二、配置管理的统一

#### 现状

各类配置项通过 `localStorage` 散落在各处读写：

- `localStorage.getItem("active_tab")` — 在 ConnectPage.vue
- `localStorage.getItem("relay_selected")` — 在 FlashConnect.vue
- `localStorage.getItem("revamp_node_selected")` — 在多处
- `localStorage.getItem("gaoji_room_name")`、`gaoji_room_password` 等 — 在 GaojiConnect.vue
- `localStorage.getItem("player_name")` — 在 App.vue
- `localStorage.getItem("window_state")` — 在 App.vue

key 分散难以统一维护，且类型安全依赖手动 `as` 断言。

#### 建议方向

**2.1 引入统一的配置管理层**

```typescript
// lib/persistConfig.ts
// 一个可扩展的配置模块，所有持久化配置通过它读写
// 支持：类型推断、默认值、自动序列化、变更监听
```

集中在一处定义所有配置项的 key、类型、默认值，各组件通过统一接口读写：

```typescript
// 定义
const config = {
  activeTab:        { key: "active_tab",        default: "quick" as const },
  relaySelected:    { key: "relay_selected",     default: "__auto__" },
  revampNode:       { key: "revamp_node_selected", default: "" },
  playerName:       { key: "player_name",        default: "玩家" },
  windowState:      { key: "window_state",       default: null as WindowState | null },
  gaoji: {
    roomName:       { key: "gaoji_room_name",    default: "" },
    roomPassword:   { key: "gaoji_room_password", default: "" },
    // ...
  },
};
```

**收益**：
- 所有配置 key 一目了然，新增/修改/删除一处完成
- 自动类型推断，消除 `as` 断言
- 可统一加版本迁移逻辑（当结构变化时自动升级旧数据）
- 可统一加变更回调（例如配置变化时自动保存到后端）

### 三、类型安全完善

#### 现状

- 部分位置使用了 `ref<any>(null)`（GaojiConnect.vue 的 `gaojiRef`）
- API 返回结果大量使用 `as string`、`as number` 的类型断言
- 部分 `catch` 块完全静默吞掉错误

#### 建议方向

**3.1 补齐 API 层返回类型**

`lib/api/*.ts` 中的 invoke 调用已有较好的类型定义（如 `invoke<PersonalizationSettings>`），但部分调用点返回值未被正确推导。可对齐各 API 函数的返回类型，确保组件层不需要手动 `as`。

**3.2 模板 ref 的类型标注**

```typescript
// 使用 InstanceType 替代 any
const gaojiRef = ref<InstanceType<typeof GaojiConnect>>(null);
```

### 四、KeepAlive 下的生命周期管理

#### 现状

`GaojiConnect.vue` 在 `onUnmounted` 中清理事件监听（`listen("app-log")`、`listen("latency-update")`），但由于 App.vue 使用 `<KeepAlive>` 包裹页面组件，组件切页时不会触发 `onUnmounted`，多次切回可能导致事件重复绑定。

#### 建议方向

- 对于可能被 `<KeepAlive>` 缓存的组件，同时在 `onDeactivated` / `onUnmounted` 中清理
- 或在 composable 层面封装生命周期管理，统一处理 `onMounted` + `onActivated` 的绑定和对应清理

### 五、样式系统梳理

#### 现状

全局样式分布在多处：
- `App.vue` 的 `<style>` 约 400 行（CSS 变量、主题定义、全局 reset、dialog 样式）
- `assets/design-system.css`（间距、字号、圆角等设计 Token）
- `assets/animations.css`（动画关键帧）
- `assets/fonts.css`（字体声明）

Dialog 的全局样式（`.dialog-overlay`、`.dialog-card` 等）定义在 App.vue 而非 Dialog.vue 中，存在不同步风险。

#### 建议方向

- 整理 CSS 职责边界，将全局性样式统一归入 `design-system.css`
- Dialog 相关样式移至 Dialog.vue 的 scoped style 中
- 利用 CSS 自定义属性的级联特性，减少 JS 操作样式的场景

---

### 六、其他可考虑的点

- **日志虚拟化**：当前日志 200 条上限，如需展示更多可考虑虚拟列表
- **Toast 升级**：增加图标类型、可交互操作、按类型分色，提升通知体验
- **错误处理规范化**：统一错误捕获和用户提示的格式，消除静默 `catch {}`
